# Track B (Green & Resilient City: Climate Action): data availability and feasibility for B1 HeatGuard, B2 FloodSense, B3 ZeroWaste Navigator

Method note: most findings below come from calling the data.gov.sg APIs directly on 2026-09-23 SGT. I (a) listed the full data.gov.sg catalogue via `api-production.data.gov.sg/v2/public/api/datasets` (4,629 datasets), (b) called every relevant v2 real-time endpoint live and with `?date=` for history, (c) called `datastore_search` on the CSV datasets, and (d) downloaded and parsed the GeoJSON files. For those facts the "source" is the dataset page or endpoint URL. Counts such as station numbers are what the API returned on that date. Anything I could not check directly is listed under Gaps.

## Cross-cutting: data.gov.sg APIs, historical depth, rate limits and Databricks fit

### Takeaway
All weather data for Track B comes through one v2 real-time API (`api-open.data.gov.sg/v2/real-time/api/...`). It returns past data when you pass `?date=YYYY-MM-DD`, back to 2016 or 2017 for temperature, humidity and rainfall, from Feb 2025 for WBGT, and only from about Oct 2025 for flood alerts. Each call returns 25 readings and a pagination token. Without an API key the limit is 6 calls per 10 s, so for bulk history the yearly "Historical … (YYYY)" CSV datasets (2016–2024) should be the main source. The API should only fill 2025 and 2026.

### Cited Findings
- v2 rate limits, reset every 10 s. Real-time API: 6 calls (no key), 12 (dev key), 30 (prod key). Datastore Search: 4 / 8 / 20. Dataset downloads: 2 / 4 / 10. Going over returns HTTP 429. Keys come from signing up on data.gov.sg — [data.gov.sg API rate limits](https://guide.data.gov.sg/developer-guide/api-overview/api-rate-limits)
- In my tests the no-key limit was hit after about 3–4 quick calls. The error text was "Rate limit exceeded… sign up for an API key for higher rate limits" (code 24, TOO_MANY_REQUESTS) — [api-open.data.gov.sg rainfall endpoint](https://api-open.data.gov.sg/v2/real-time/api/rainfall)
- Historical calls return 25 records per page plus a `paginationToken`. Examples: `air-temperature?date=2017-01-01`, `rainfall?date=2020-06-01` and `weather?api=wbgt&date=2025-06-01` all returned 25 records and a token — [air-temperature API](https://api-open.data.gov.sg/v2/real-time/api/air-temperature)
- Temperature readings are 1-minute values (readingType "DBT 1M F"). Rainfall readings are 5-minute totals ("TB1 Rainfall 5 Minute Total F"). So one day is about 1,440 temperature timestamps (~58 pages) or 288 rainfall timestamps (~12 pages). The flood-alerts endpoint returned 722 records in 29 pages for 2026-02-18 — [air-temperature API](https://api-open.data.gov.sg/v2/real-time/api/air-temperature); [rainfall API](https://api-open.data.gov.sg/v2/real-time/api/rainfall)
- The CSV datastore also works for bulk history. Historical Rainfall 2024 (`d_a0b69d3e02576a1fd0ab673e71f83507`) has 6,406,260 rows. Historical Air Temperature 2024 (`d_910c81fce47f38574015b3882ac59254`) has 6,868,395 rows. Both have the fields date, timestamp, station_id, station_name, lat/lon, reading_value, reading_type and reading_unit — [Historical Rainfall 2024](https://data.gov.sg/datasets/d_a0b69d3e02576a1fd0ab673e71f83507/view)
- GeoJSON and CSV files download through `https://api-open.data.gov.sg/v1/public/api/datasets/<id>/poll-download`, which returns a signed URL (tested for recycling bins, e-waste, parks, hawker centres and planning areas) — [Recycling Bins](https://data.gov.sg/datasets/d_4dde14826642f49eefff48b7832b90db/view)
- Free Edition limits: serverless only, one 2X-Small SQL warehouse, up to 5 concurrent job tasks, one active Lakeflow pipeline per type, limited model-serving endpoints (no GPU), up to 3 Apps. Compute can be suspended for the day if quotas are exceeded — local file `docs/guidelines/databricks-free-edition_setup_and_limits.txt`

### Inferences
- Rough backfill cost for 2025-01 to 2026-09 through the API, since no 2025 CSVs are in the catalogue: rainfall is about 630 days × 12 pages ≈ 7.5k calls, about 3.5 h with no key or about 45 min with a prod key. Temperature at 1-minute resolution is about 36k calls, about 17 h with no key. **Get a dev or prod key on day 1.** Also consider sampling temperature (for example one page per hour) or using the monthly or annual climate CSVs instead.
- A scheduled notebook job every 5–15 minutes that appends to a Delta table covers the "live stream" requirement cheaply. One Lakeflow pipeline can do the bronze→silver→gold steps. Both fit inside Free Edition limits.

### Gaps
- I could not check whether Free Edition serverless compute can reach `api-open.data.gov.sg` (outbound internet or egress rules). **Test this on day 1.** If it is blocked, the fallback is to pull data locally and upload it to a Volume.
- The rate-limit page does not give the HTTP header name for the API key. I believe it is `x-api-key` but have not verified this.
- I did not check the size in MB of the historical CSV downloads.

## B1 HeatGuard: stations, humidity, WBGT, PM2.5, historical depth, forecasting, outcome data, demographics

### Takeaway
B1 is **the most data-ready problem in Track B**, but the brief is wrong in several ways. There are **16 air-temperature stations, not "~50"**. Relative humidity is available at the same 16 stations. **NEA publishes an official WBGT and heat-stress-level API with 30 stations**, with history from 11 Feb 2025. PM2.5 is **5 regions, hourly**. The "HDB Elderly Population by Planning Area / by block" dataset **does not exist as described**: the HDB data is by town, only for survey years 2003/2008/2013/2018. The "Senior Activity Centres" locations file is 2016 vintage. There is no open outcome data on heat illness by area, so the "ML Heat Risk Score" has to be a composite or unsupervised score, or a forecast of WBGT, not a classifier trained on health outcomes.

**Outcome data**
- MOH figures (via press): heat-related illness cases at public-hospital EDs rose from 280 (2024) to 398 (2025). Admissions went from 69 to 81. One heat-related death was recorded in 2021–2024. National totals only. A Sept 2026 article describes researchers working to *improve* heat illness data at A&Es — [Yahoo News / Straits Times](https://sg.news.yahoo.com/researchers-mission-improve-heat-illness-210000050.html)
- The catalogue has only generic hospital admission tables (e.g. "Hospital Admission Rate By Sex And Age, Annual", `d_e2acb8eaf4eaf1e0a1608af9a9cd2634`). None is heat-specific or by area — [data.gov.sg](https://data.gov.sg/datasets/d_e2acb8eaf4eaf1e0a1608af9a9cd2634/view)

### Inferences
- The "live heat index dashboard" can be built directly. Use the **official WBGT and heatStress feed (30 stations)** as the headline stream. Temperature + RH (16 stations) can back a computed heat index as a cross-check. This meets "at least two real-time streams" (WBGT + temperature/RH, or + PM2.5 / 2-hour forecast).
- Scoring by planning area needs spatial interpolation. With 30 WBGT and 16 temperature stations across 55 planning areas, many areas have no station. Use nearest-station or IDW, and be upfront about it (this helps the "data rigour" score).
- The Heat Risk Score can combine hazard (interpolated WBGT or its percentile), exposure (65+ population from Census 2020 or the SingStat June 2025 file) and vulnerability (share of 1–2-room rental flats, block age from HDB Property Info, disability prevalence from Census). Cooling access comes from distance to CCs, hawker centres, parks and the 2016 SAC points. Low/Med/High can follow NEA's own heatStress thresholds. **"ML" can honestly mean clustering or a WBGT forecast model, not a supervised risk classifier**, because there are no area-level outcome labels.
- A next-day forecast is feasible. Train on temperature/RH history (2016–2024 CSVs plus the 2025–26 API) and use the 24-hour or 4-day forecast (national high/low temperature and RH) as features, to predict tomorrow's per-station max temperature or WBGT. WBGT has only about 19 months of labels, so an alternative is to estimate WBGT from temperature/RH/wind. Either is doable in 2 weeks with MLflow.
- Overall: **high feasibility**. The main risks are small: the flawed dataset list in the brief (which judges may not notice) and the need to get geocoding right.

### Gaps
- I did not verify the exact numeric WBGT cut-offs NEA uses for Low/Moderate/High. The press release refers to an infographic. The API gives the label directly.
- I could not confirm whether an up-to-date Active Ageing Centre locations dataset exists (for example from AIC or SG Enable). None is in the data.gov.sg catalogue.
- I did not verify the SingStat June 2025 planning-area file's columns (whether 65+ bands are present).
- The WBGT start date is somewhere between 2025-01-01 (404) and 2025-02-01 (data), consistent with the 2025-02-11 coverageStart in the metadata.

## B2 FloodSense: flood alert history, flood-prone records, labels, rainfall depth and classifier credibility

### Takeaway
Rainfall data is rich: 89 live 5-minute stations, yearly CSVs for 2017–2024, and API history back to 2017. **Flood labels are the problem.** "Flood Prone Areas (Annual)" is literally **4 rows of national hectare totals** (27 → 24.1 → 23.6 → 23.3 ha, 2022–2025). Flood Alerts has a usable schema (CAP messages with lat/lon/radius), but its **API history only starts around October 2025**, and actual alerts are rare (one event on the notable 18 Feb 2026 flood day). A supervised Low/Med/High classifier trained on "rainfall × flood co-occurrence" would have very few positive labels. It would need to rely on PUB's static lists of 36 flood-prone areas and the hotspots PDFs, so its credibility would be weak unless it is framed honestly.

### Cited Findings
- Flood Prone Areas (`d_c4aed98f1533eb3a66f65dbb1a30da46`, PUB, CSV of 57 bytes, last updated 2026-05-25): columns Year and Hectares, **4 rows: 2022 = 27, 2023 = 24.1, 2024 = 23.6, 2025 = 23.3** — [data.gov.sg](https://data.gov.sg/datasets/d_c4aed98f1533eb3a66f65dbb1a30da46/view)
- PUB's PDF "List of Flood Prone Areas in Singapore (Updated as at 31 Jan 2024)" names **36 locations** by road name only (e.g. Alexandra Rd/Jervois Rd, Beach Rd, Jalan Besar Area, Sennett Estate, Upp East Coast Rd/Parbury Ave), with no coordinates. It defines flood-prone areas as "low-lying, with a history of flooding" — [PUB PDF](https://www.pub.gov.sg/-/media/PUB/Flood-Resilience/Documents/List-of-Flood-prone-Areas-in-Singapore.pdf)
- PUB's About Floods page links a newer Flood-Prone Areas list (Nov 2025) and a "Hotspots in Singapore" list (Feb 2026). It states flood-prone areas fell from about 3,200 ha in the 1970s to under 25 ha. It gives no event-level records or downloads beyond the PDFs — [PUB About Floods](https://www.pub.gov.sg/Public/KeyInitiatives/Flood-Resilience/About-Floods)
- Flood Alerts across Singapore (`d_f1404e08587ce555b9ea3f565e2eb9a3`, PUB, API, created 2025-09-03): "real-time flood alert events… Flood warning notices are not included", updated every 2 minutes. Endpoint: `/v2/real-time/api/weather/flood-alerts` (also `weather?api=flood-alerts`) — [data.gov.sg](https://data.gov.sg/datasets/d_f1404e08587ce555b9ea3f565e2eb9a3/view); [metadata](https://api-production.data.gov.sg/v2/public/api/datasets/d_f1404e08587ce555b9ea3f565e2eb9a3/metadata)
- Flood Alerts schema, confirmed from a real record (2026-02-18 17:51). It is a CAP-style message with identifier, msgType (Alert / Cancel), and readings[] containing severity ("Moderate"), urgency, certainty ("Observed"), headline "Flash Flood Alert", description ("Flash flood at Jurong Town Hall Road from Jurong East Street 11 to Jurong East Street 12…"), and **area.circle [lat 1.32936, lon 103.74325, radius 0.05]**. A matching "Cancel" message ("Flash flood subsided… Issued 1804 hours") lets you compute duration — [flood-alerts endpoint](https://api-open.data.gov.sg/v2/real-time/api/weather/flood-alerts?date=2026-02-18)
- Flood Alerts history depth: `date=` returned records for 2025-10-15, 2025-11-01, 2025-12-01, 2026-01-01 and 2026-03/06/08/09. It returned empty for 2025-10-01, 2025-04-01, 2025-03-01, 2025-01-01 and 2024-01-01. **So history starts in the first half of Oct 2025, about 11 months.** Most records are empty "heartbeat" polls every 2 minutes. 2026-02-18 had 722 records, of which only 2 carried an alert (one alert and one cancel) — [flood-alerts endpoint](https://api-open.data.gov.sg/v2/real-time/api/weather/flood-alerts)
- Press confirms flash floods at Jurong Town Hall Road on 18 Feb 2026 and a flash-flood *warning* for parts of Katong on 17 Feb 2026. Warnings are not in the API — [Mothership](https://mothership.sg/2026/02/pub-flash-flood-west-singapore/); [AsiaOne](https://www.asiaone.com/singapore/flash-floods-jurong-cny-day-2); [Mothership Katong](https://mothership.sg/2026/02/risk-flash-floods-katong-pub/)
- Rainfall history: yearly "Historical Rainfall across Singapore" CSVs exist for **2016 (only 2016-12-02 to 12-03)** and **2017–2024** (e.g. 2017 `d_1990a5a1aeaf3dd243cf4dae294a61c4`, 2019 `d_61995f092320e7155b7528050880b502`, 2023 `d_f864cc30d58b467db83659ad17c737bf`, 2024 `d_a0b69d3e02576a1fd0ab673e71f83507` with 6.4M rows). **No 2025 CSV.** The API `rainfall?date=` returns 404 for 2016-12-01 and data from 2017-01-01 (56 stations listed that day) and 2020-06-01 (48 stations) — [Historical Rainfall 2024](https://data.gov.sg/datasets/d_a0b69d3e02576a1fd0ab673e71f83507/view); [rainfall endpoint](https://api-open.data.gov.sg/v2/real-time/api/rainfall)

- PUB Water Level Sensors (`d_31333fa5cf0834f012d840365b336610`, XLSX): **328 sensor locations** (Station ID, Name, SVY21 X/Y, e.g. "CWS193 Harvey Rd/ Macpherson Rd"). **Metadata only, no readings on data.gov.sg.** Live levels appear on PUB's own site — [data.gov.sg](https://data.gov.sg/datasets/d_31333fa5cf0834f012d840365b336610/view); [PUB water level sensors page](https://app.pub.gov.sg/waterlevel/pages/waterlevelsensors.aspx)
- Other real-time inputs: Lightning Observation API (`d_08238953fe0f6dd13f10714ebfbcb9f9`, from 2025-02-11) and Weather Radar Images API (`d_418e9ac3414fd927b7405631e0a7bc82`, from 2026-07-01), which could support nowcasting — [Lightning](https://data.gov.sg/datasets/d_08238953fe0f6dd13f10714ebfbcb9f9/view); [Radar](https://data.gov.sg/datasets/d_418e9ac3414fd927b7405631e0a7bc82/view)
- Academic flood inventories exist (Straits Times archive 1892–2015; one study extends to 176 events over 1985–2020), but they are not an open dataset — per search result summary of [ResearchGate figure](https://www.researchgate.net/figure/Frequency-of-total-number-of-reported-Singapore-floods-categorised-into-flash-floods-and_fig2_304032085) (secondary; not verified in full)

### Inferences
- **The "3-year time-series trend analysis of flood-prone areas" is 4 numbers.** It works as a single chart or KPI tile, not as analysis.
- Labels could come from (a) flood-alert events since about Oct 2025, likely tens of events at most, and (b) the 36 flood-prone roads plus hotspots, geocoded to points and buffered. Neither supports a credible supervised Low/Med/High classifier at zone × time resolution. A defensible design is:
  - a hazard score from observed or nowcast rainfall intensity (5-min, 30-min and 60-min rolling totals at the nearest gauges, plus 2-hour forecast and lightning), multiplied by
  - a static susceptibility layer (distance to flood-prone or hotspot roads, water-level sensor density, low-lying proxies),
  - then validated against the flood-alert events since Oct 2025 as a small out-of-sample check.
  A classifier "trained" only on a year of alerts should be presented as a prototype with its limitations stated.
- The streaming part is easy: scheduled polling of rainfall every 5 minutes and flood alerts every 2 minutes. Batch history (8 years of 5-minute rainfall, about 6M rows a year) is fine on serverless.
- Stretch goals: LTA ridership is only available in aggregated or monthly form (not verified here). The sea-level-rise layer has no open raster in the catalogue. Both are weak.
- Overall: **medium-low feasibility against the "winning demo" as written, mainly because of labels.** It is feasible as a well-framed risk-scoring tool.

### Gaps
- I did not count total flood-alert events from Oct 2025 to Sep 2026. A full scan is about 29 pages/day × 350 days ≈ 10k calls, too slow without a key.
- I did not retrieve the Nov 2025 flood-prone list or the Feb 2026 hotspots PDF contents or counts.
- I did not verify total rainfall station counts per historical year from the CSVs. The datastore `distinct` query was not supported.
- I did not check whether PUB exposes historical water-level readings anywhere openly.

## B3 ZeroWaste Navigator: waste series, recycling bins, e-waste points, per-planning-area coverage

### Takeaway
The national series are good: SingStat "Waste Management and Overall Recycling Rates, Annual" covers **2000–2025 (26 years) by 14 waste types**, and "Waste Disposed Of And Recycled" covers 2013–2025. **Everything is national. There is no planning-area waste or recycling tonnage.** The Recycling Bins GeoJSON has **12,578 points, all tagged as HDB addresses, with records last stamped 2017**. It therefore reflects the one-bin-per-HDB-block pattern rather than true service gaps, and it has nothing for condos or landed estates. Per-planning-area "bins per 1,000 residents" can be computed but mostly measures the share of HDB housing. E-waste has 718 points (2021–2022 records).

### Inferences
- Coverage per planning area can be computed: spatial-join the 12,578 bins and 718 e-waste points to the 55 planning-area polygons, then divide by Census population or households. **But the result is mostly a reflection of HDB share.** Condo and landed areas will look "underserved" partly because private estates (condo chutes, landed-estate bins) are not in the dataset. Bins per HDB dwelling unit, using HDB Property Info, is the fairer measure and should be stated as a limitation.
- The "ML-projected trajectory to 2030" rests on about 26 annual points per series. Simple trend or ARIMA models with prediction intervals are adequate; anything more complex overfits. COVID (2020 dip) needs handling.
- "Top 5 planning areas for investment" and "before vs after intervention" can only be **scenario simulations with assumed elasticities** (for example, one extra bin per X households gives +Y% domestic recycling). No area-level outcome data exists to calibrate against. That is acceptable if presented transparently.
- Real-time streams are essentially absent in B3, which is weaker on "technical execution on Databricks" (streaming). It is simpler to build, though: all batch.
- Overall: **high buildability, but modest analytical depth and a risk of looking like a "generic dashboard"** (Round 1 penalises this under originality).

### Gaps
- The domestic recycling rate (as opposed to overall) is not in the SingStat table checked. NEA publishes it on its waste statistics page, which I did not verify here.
- I did not verify the Zero Waste Masterplan 2030 targets (my recollection is 30% less waste to landfill per capita per day, 70% overall recycling, 30% domestic, 81% non-domestic). The brief's "30% reduction" is likely the landfill-per-capita target, not total waste.
- I did not check whether NEA has a newer bin dataset (for example on OneMap themes) that includes private estates or a 2024+ refresh.

## Overall buildability ranking for a student team (2 weeks, Databricks Free Edition)

### Takeaway
**B1 HeatGuard is the strongest choice**: an official WBGT feed plus temperature/RH streams, planning-area demographics, a forecastable target, and a clear social-impact story. **B3** is easiest to build but hard to make original and has no live streaming. **B2** has good rainfall data but the thinnest and shortest flood labels, so its headline "classifier" is the hardest to defend to judges on data rigour.

### Cited Findings
- Judging: Round 1 weights Data and technical feasibility at 25% ("named open datasets, a credible Databricks architecture, and buildable in two weeks") and Originality at 30% ("not a generic dashboard"). Demo Day: Technical execution 30%, Data rigour 10% ("honest limitations") — local file `docs/guidelines/judging-criteria.txt`
- Evidence summarised above: WBGT with 30 stations and history from Feb 2025 ([WBGT dataset](https://data.gov.sg/datasets/d_87884af1f85d702d4f74c6af13b4853d/view)); flood alerts history from about Oct 2025 and a 4-row flood-prone CSV ([Flood Prone Areas](https://data.gov.sg/datasets/d_c4aed98f1533eb3a66f65dbb1a30da46/view)); recycling bins all HDB, dated 2017 ([Recycling Bins](https://data.gov.sg/datasets/d_4dde14826642f49eefff48b7832b90db/view))

### Inferences
- **B1: feasible, low risk.** Architecture: a job polls WBGT, temperature, RH and PM2.5 every 5–15 minutes into bronze Delta tables. One Lakeflow pipeline builds silver/gold. Gold tables join per-station readings to planning areas via IDW, plus the Census 65+ population, HDB block vulnerability and cooling-asset distances. An MLflow-tracked next-day WBGT or Tmax forecast feeds an AI/BI dashboard or a Databricks App with Low/Med/High tiers and alert text (an optional LLM via Foundation Model API). Honest caveats: sparse stations, no outcome labels, 2020 Census or June 2025 SingStat demographics, and 2016-era SAC points.
- **B2: feasible only when reframed.** Rainfall-intensity nowcast plus susceptibility, validated on about 11 months of alerts. It is risky if judges expect a true trained classifier.
- **B3: feasible, low technical risk, low novelty.** The stale, HDB-only bin data weakens the headline "gap" analysis, and it has no real-time component.
- Brief errors to flag in any proposal (this earns data-rigour credit): about 16 temperature stations, not about 50. PM2.5 is hourly by 5 regions, not 15-minute. The HDB elderly data is by town for 2003–2018 only, not by block or planning area. There are no historical rainfall CSVs for 2025, and 2016 covers only 2 days. Flood Prone Areas is 4 national numbers.

### Gaps
- I did not test outbound HTTP from Free Edition serverless. This is the critical pre-check for all three problems.
- I did not survey GitHub for prior projects using these APIs.
